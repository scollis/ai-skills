# S-TABLE - Stabilized Platform

The AMF2 Roll-Pitch-Heave (RPH) stable platform is a hydraulic three-leg table deployed on ocean-going vessels (e.g., container ship Horizon Spirit) that actively compensates for ship roll and pitch (and maintains constant height against heave) to keep instruments such as the Marine W-band Cloud Radar (MWACR) pointed in the zenith direction.

## How it measures

The platform uses three independently hydraulically controlled legs (A, B, C) with position encoders to tilt the table in roll and pitch, while a mathematical constraint (Bl + (Al+Cl)/2 = 2D) keeps the table at constant height to compensate for heave. A Galil DMC-21X3 motion controller drives the legs based on commanded position, speed, and acceleration. Control is achieved via a PID feedback loop using an error function derived from a tilt sensor (or ship navigation system) measurement of roll/pitch versus desired values, driving the error toward zero. Because compensation is never instantaneous due to mechanical and computational delays, a predictive algorithm (based on polynomial extrapolation of previous platform positions and ship motion data) is combined with the PID to anticipate platform position several samples in advance, forming a 'modified PID' approach. A precomputed lookup table relates encoder positions (Al, Bl, Cl) to unique roll/pitch angle pairs within ±15°, generated by exercising the table through its full range of encoder values and measuring resultant angles with a ship navigation sensor.

**Siting.** Seaborne Navigation System (SeaNav/Hydrins) placed at or near the centerline of the ship; RPH table located on a flat open area behind the bridge; tilt sensor mounted at center of table below the MWACR; canvas skirt used to keep water from encroaching on electronics; table used for instruments requiring zenith-pointing/vertical orientation such as cloud radars.

**Sampling.** native rate Ship navigation datastream (SeaNav/Hydrins) at 50 Hz; reported every Sub-sampled at a selectable rate; 17 Hz used aboard Horizon Spirit; averaging Performance statistics computed over roughly hour-long periods, 15-minute averages, and 5-minute standard deviation calculations at 20 Hz sampling; probability distributions sampled at 4 Hz (hb p. 12).

## Getting the data

ARM Live needs `ARMUSER` / `ARMTOKEN` credentials; see the `act-arm-live` skill for the
service, datastream naming and the server-side subset endpoint.

The `act-arm-live` and `act-qc` skills wrap these calls in shorter helpers
(`armlive_open`, `armlive_list_files`, `act_qc_table`, `act_qc_apply`). Those are helpers
those skills define, **not** ACT functions - nothing below uses them, so every block here
runs against a bare `act-atmos` install.

```python
import os, requests, act

user, token = os.environ["ARMUSER"], os.environ["ARMTOKEN"]

# ACT has no list-only call, so size the request against ARM Live's query endpoint
# before transferring anything.
avail = requests.get("https://adc.arm.gov/armlive/livedata/query",
                     params={"user": f"{user}:{token}", "ds": "marrphtiltM1.a1",
                             "start": "2018-03-21", "end": "2018-03-21", "wt": "json"}).json()
print(avail["num_found"], avail["total_size"])            # files, bytes

# Downloads into ./marrphtiltM1.a1/ unless you pass output=
files = act.discovery.download_arm_data(user, token, "marrphtiltM1.a1", "2018-03-21", "2018-03-21")
ds = act.io.arm.read_arm_netcdf(files, cleanup_qc=True)
print(act.discovery.get_arm_doi("marrphtiltM1.a1", "2018-03-21", "2018-03-21"))   # cite what you pulled
```

## Quality control in this datastream

This datastream ships **no `qc_` companion variables**, so `act-qc`'s filter methods
have nothing to act on. Screening has to come from the fields the product provides
itself and from Data Quality Reports.

Either way, check the DQRs before trusting a period - they carry the mentor's knowledge
of icing, misalignment and outages that no automated test catches:

```python
act.qc.print_dqr("marrphtiltM1.a1", "20121001", "20260923")
```

The handbook's own note on data quality: Performance evaluated via mean and standard deviation of ship vs. table roll, pitch, and resultant tilt, plus ratio of table-to-ship values; probability distributions (1D and 2D) and cumulative probability distributions of tilt used to assess how close to level the table remains (greater than 90% within 0.1°, greater than 99% within 0.5° in moderate MAGIC campaign conditions). Statistics tabulated by cruise number and direction (Table 2) including roll, roll std, roll ratio, pitch, pitch std, pitch ratio.

## Known artifacts and failure modes

From the handbook. This is the section to read before concluding that a feature in
the data is atmospheric.

| issue | how it shows up | what the handbook says to do | source |
|---|---|---|---|
| Roll/pitch extremes not simultaneously achievable | Table cannot reach maximum roll and pitch at the same time; only combinations within ± 15° are jointly achievable, limiting compensation range in severe combined tilt conditions | Design parameter accepted; data from other instruments unlikely to be viable outside this range anyway | (hb p. 8) |
| Tilt sensor resolution limit (0.1°) | Pitch values show stepped/quantized appearance in time series because they are small and near the 0.1° resolution floor | None specified beyond noting the limitation | (hb p. 13) |
| Kearfott SeaNav navigation system failure | Enhanced/modified PID (using ship navigation data) could not be used for extended period (Nov-Dec 2012); system fell back to straight PID using only local tilt sensor feedback | Replaced with Hydrins system in December 2012; operated in fallback tilt-sensor-only feedback mode in interim | (hb p. 12) |
| Leg malfunction on cruise 7B | Cruise number 7B missing from data/results because one table leg malfunctioned and could not be repaired until reaching port | Repaired in port | (hb p. 18) |
| Table pointed at nonzero offset (−1°) during cruise 5A | Tilt values and probability distributions for cruise 5A show an additional distribution of table values around 1° rather than centered at 0° | Noted explicitly when interpreting Figure 11 and subsequent distributions | (hb p. 18) |
| Inappropriate feedback values during enhanced PID use (cruises 8B, 9B) | Larger table tilt values observed during 8B and 9B attributable to enhanced PID routine run with inappropriate feedback parameters | None specified beyond identification | (hb p. 18) |
| Unresolved alignment/offset between MWACR IMU and radar antenna | Static offset between MWACR and tilt sensor positions, contributing to systematic roll/pitch bias | No control over this offset; noted as unresolved | (hb p. 27) |
| Unresolved alignment/offset between MWACR IMU and table tilt sensor | Static offset of approximately −0.9° in roll and 0.6° in pitch between tilt sensor and IMU observed during installation | Capability to point table at arbitrary reference angle (not just 0) incorporated into RPH software to compensate; actual offset value still needs... | (hb p. 27) |
| Watson tilt sensor dynamic response inadequacy | Time series comparison shows Watson sensor registers ship motions (e.g., at 70455 and 70470 seconds) not evident in MWACR IMU; Watson shows different periodicity and consistently overshoots... | Recommend using MWACR IMU data directly to control RPH instead of Watson tilt sensor, eliminating the table-to-MWACR alignment problem; being... | (hb p. 27) |
| Table rest position not parallel to ship deck | Arbitrary offset seen in roll time series when table is not operating, since resting table orientation differs from ship deck orientation | Noted as source of offset in Figure 17 comparison; offsets removed for precise comparison in Figure 18 | (hb p. 27) |
| Unknown adequacy for cloud vertical velocity measurements | Not established whether achieved leveling performance (0.1°, 90% of time) is sufficient for MWACR vertical velocity measurement requirements, as opposed to radiometry | Flagged as an open question for further evaluation | (hb p. 26) |
| Absolute accuracy of local tilt sensor uncertain | Performance values depend entirely on the local tilt sensor used, and its absolute accuracy is questioned; does not affect table's demonstrated relative representative capability | None specified; noted that table would respond equally well to any alternative local error measurement | (hb p. 19) |


## Calibration and maintenance

|  |  |
|---|---|
| Calibration method | Table lookup function developed by exercising the table through the complete range of encoder values at 50 encoder count increments and measuring resultant roll/pitch with SeaNav sensor placed at table center, then inverting the table so desired pitch/roll map to encoder position indices (hb p. 9) |
| Calibration interval | One-time characterization taking roughly a 40-hour operation (hb p. 9) |
| Routine maintenance | Legs do not require re-zeroing after power loss because leg lengths are uniquely associated with encoder values; repairs to malfunctioning legs require reaching port (hb p. 9) |


Calibration history matters for trend work: a step at a calibration date is an
instrument event, not a climate signal.
